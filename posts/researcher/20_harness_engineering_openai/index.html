OpenAI 的 Harness Engineering 实验：零人工代码的百万行产品

一行代码都不手写，能造出什么？

引言：一场五个月的疯狂实验

过去五个月，OpenAI 内部悄悄进行了一场前所未有的实验：

构建并交付一款软件产品的内部 beta 版，其中没有一行代码是人工编写的。

这不是概念验证，不是 demo，而是一个有内部日常活跃用户和外部 Alpha 测试者的真实产品。它经历了交付、部署、故障和修复的完整流程。

结果令人震惊：仅用约 1/10 的传统开发时间，完成了一个包含近百万行代码的项目。

人类掌舵，智能体执行。这不是噱头，而是正在发生的工程现实。

实验结果：数字说话

指标数据
项目周期5 个月
总代码量~100 万行
PR 合并数~1,500 个
工程师团队初始 3 人，后扩至 7 人
人均 PR/天3.5 个
时间节省约 90%（对比传统开发）
产品状态已有内测用户日常使用

更令人惊讶的是：随着团队规模从 3 人扩大到 7 人，吞吐量不降反升。

核心理念：不做"人工工程师"

团队立下了一条铁律：不手动编写代码（No Hand-Written Code）。

人类工程师的工作发生了根本性转变：

以前：写代码 → 评审 → 部署
现在：设计环境 → 明确意图 → 构建反馈回路 → 智能体执行

工程师的角色从代码编写者变成了系统架构师和意图翻译官。

核心挑战一：情境管理

AI 智能体在复杂任务中最大的瓶颈是什么？情境（Context）管理。

团队最先尝试的方法是"一本大型 AGENTS.md 说明书"——结果失败了：

  • 情境是稀缺资源：一份巨大的指令文件会挤掉任务代码和文档
  • 过多指导等于无效：当一切都"重要"时，智能体无法判断优先级
  • 文件会腐坏：庞杂的手册变成过时规则的坟场
  • 无法验证：单个 blob 不适合做机械检查，漂移不可避免

解决方案：地图 ≠ 说明书

团队将 AGENTS.md 重新定位为内容目录，而不是百科全书：

AGENTS.md（约 100 行） → 地图 → 指向 docs/ 中的深层真实信息

docs/ 目录被当作记录系统（Source of Truth），包含：

  • 设计文档（已编目、索引、验证状态）
  • 架构文档（顶层域和包分层地图）
  • 执行计划（一流的工件，带进度和决策日志）
  • 技术债追踪

知识以**渐进式披露（Progressive Disclosure）**的方式组织——智能体从小而稳定的入口开始，而不是被一开始就淹没。

核心挑战二：架构约束先行

在传统开发中，架构约束往往要等到团队规模达到数百人时才被迫建立。

对于 AI 智能体来说，这是早期的先决条件：

没有约束 → 速度下降 → 架构漂移

团队构建了一套严格的架构模型：

Types → Config → Repo → Service → Runtime → UI

每层只能向前依赖，依赖方向经过严格验证。跨切关注点（认证、连接器、遥测）通过统一的 Providers 接口注入。

这套规则由自定义 linter + 结构化测试机械强制执行——而这些 linter 本身也是 Codex 生成的。

核心挑战三：可观测性下沉

为了让 Codex 能真正"自主工作"，团队把应用程序变成智能体可直接读取的形式：

  • 日志、指标、追踪记录 → 通过本地可观测性堆栈展示给 Codex
  • 应用程序按 git worktree 启动 → Codex 可为每次变更启动独立实例
  • Chrome DevTools 协议接入 → Codex 可复现 bug、截图、验证修复

结果：单次 Codex 运行可以在一个任务上持续工作超过 6 小时（通常是人类睡眠时间）。

重大突破：端到端自主

五个月后，团队跨过了一个重要门槛：Codex 现在可以端到端驱动一个完整的新功能。

给定一个提示，智能体现在可以自主完成：

  1. 验证代码库当前状态
  2. 重现已报告的 bug
  3. 录制故障演示视频
  4. 实施修复
  5. 通过运行应用程序验证修复
  6. 录制解决方案演示视频
  7. 打开 Pull Request
  8. 回应智能体和人类反馈
  9. 检测并修复构建故障
  10. 合并更改（仅在需要判断时才交由人工）

持续性问题：AI 残渣清理

智能体生成的代码也会"遗传"代码库中已有的不良模式。随着时间推移，漂移不可避免。

团队的解法：Golden Rules（黄金原则）

每周 20% 手工清理"AI 残渣" → 不可扩展
将黄金原则编码到代码仓库 + 循环清理流程 → 可扩展

黄金原则示例：

  • 优先使用共享工具包，而非手写辅助函数（集中管理不变式）
  • 不做"YOLO 式"数据探测（必须验证边界或依赖类型化 SDK）

技术债务像高息贷款——持续小额偿还，远优于集中一次性处理。

关键洞察：人类工程师的新杠杆

传统工程智能体优先工程
代码即产出代码是副产品，系统才是产出
人工审核合并智能体对智能体审核为主
代码审查通过率是指标人类注意力成为瓶颈
架构是后期约束架构是前置约束
技术债可延迟处理技术债必须持续小颗粒清理

最根本的变化： 工具、抽象和反馈回路的优先级提升了，而不仅仅是代码本身。

给实践者的建议

OpenAI 团队总结的经验：

  1. 先建约束，再提速度 — 架构边界必须机械强制执行
  2. 让应用对智能体可读 — 可观测性必须嵌入，不是附加
  3. 渐进式情境披露 — 不要用 1000 页说明书压垮智能体
  4. 持续清理优于突击重构 — 技术债必须按日处理
  5. 捕捉人类品味并系统化 — 将 review 反馈编码为规则或文档

结语

构建软件仍然需要纪律，但纪律更多体现在支撑结构上，而不是代码本身。

OpenAI 的实验证明了一个核心命题：AI 智能体不是来替代工程师的，而是来替代编码本身的。

当编码不再是瓶颈，人类工程师最大的价值就变成了：设计环境、明确意图、构建反馈回路。

这是一场刚刚开始的工程革命。Harness Engineering 正在重新定义"做软件"意味着什么。
